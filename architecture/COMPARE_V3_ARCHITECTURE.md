# Compare V3 architecture

## Product differentiation

Compare V3 is an interaction-intelligence system, not a compatibility-scoring system. It explains how two preference patterns may meet in observable communication, decisions, stress, repair, friendship, romance, and work. It never predicts relationship success, employment suitability, or a scientific compatibility percentage.

## Canonical page model

The 120 unique English pairs retain the existing canonical order and URL family: `/en/compare/{canonical-pair}`. Legacy `/compare/{pair}` and reverse localized pairs redirect directly to that owner. Future query evidence improves the existing page; it does not create another URL.

## Structured page schema

Each generated English pair object provides: `quickAnswer`, `atGlance`, `keyDifferences`, `commonGround`, `interactionLoop`, `communication`, `decisionMaking`, `conflict`, `stress`, `friendship`, `romance`, `work`, `emotionalNeeds`, `misunderstandings`, `scenarios`, two-way advice, learning guidance, pair myths, and visible FAQs.

The rendering order compresses related topics into a responsive two-column desktop grid and a single mobile column. Interaction loops, misunderstandings, scenarios, advice, myths, and FAQs use denser dedicated treatments. The comparison rows stack on mobile and require no horizontal scrolling.

## Interaction-intelligence model

Sixteen type lenses describe observable attention, information processing, planning, communication, conflict, stress, interpersonal needs, work contribution, and social rhythm. A pair combines both lenses with the existing relationship-intelligence decision data and personality-guide traits. The resulting content describes consequences between two tendencies rather than restating two definitions.

Priority and former experiment pages remain source foundations. Their useful introductions and topic sections are integrated where they map to V3 fields.

## Interaction loops and misunderstandings

The interaction loop records a possible signal, the need through which the other person may interpret it, the response that may follow, and the interpretation that can create friction or complementarity. Misunderstandings explicitly separate a possible signal, what may be heard, and another plausible meaning. These are illustrative tendencies, never literal scripts or certainties.

## Scenario system

A controlled scenario library covers planning, criticism, decisions, deadlines, social plans, unfamiliar problems, sudden change, emotional support, purchases, disagreement repair, shared projects, and uncertainty. Deterministic pair selection varies the situations. Each scenario combines both type lenses into Type A tendency, Type B tendency, possible friction, and a pair-specific adjustment.

## FAQ strategy

Every English pair has six visible search-intent FAQs selected around compatibility, practical difference, friendship, communication, conflict, and work. Answers incorporate pair-specific processing and conflict dynamics. FAQPage schema mirrors only these rendered questions and answers.

## Internal linking

The English hub exposes all 120 canonical URLs in server-rendered HTML. Each page links to the hub, both personality guides, selected related pairs, four Type A comparisons, four Type B comparisons, career guides, and Communication Insights. All pair links use canonical order.

## Localization policy

V3 is gated to English. Hindi continues through the existing generated Hindi contract; French and Japanese retain their authored localization packages. English fields must never be rendered beneath localized URLs. Localization of V3 requires a separate authored-content and validation project.

## Duplication safeguards

The V3 validator crawls all 120 rendered English pages, normalizes type codes and whitespace, hashes long paragraphs, and tracks repeated long sentences. It fails on identical normalized long bodies or suspicious sentences repeated across eight or more pages. Small shared interface labels, the compact no-score note, and the final CTA are excluded deliberately.

## Future GSC improvement process

Use verified Search Console queries, impressions, clicks, CTR, and position to identify an existing pair needing deeper authored treatment. Update that pair’s structured fields or source lens while preserving its canonical URL. Validate pair specificity, schema visibility, duplication, internal links, redirects, sitemap ownership, crawlability, lint, and build before release.
